# 3x-ui-telegram

Закрытый Telegram-бот для 3x-ui.

Бот работает с существующими клиентами актуальной 3x-ui. Администраторы
назначают им числовые Telegram ID. Пользователь получает только свои подключения,
QR-коды, инструкцию, состояние включения и использованный трафик.
Квоты и сроки действия не отображаются. Бот не создаёт VPN-клиентов и не принимает
заявки на доступ. Все команды и кнопки работают только в личных чатах.

Поддерживаются два способа запуска: **Vercel + Supabase PostgreSQL** через webhook
и Vercel Queues либо постоянный процесс на VPS с SQLite. Это альтернативные
способы: не запускайте polling и webhook с одним токеном одновременно.

## Vercel + Supabase

Поток обработки: Telegram → `/api/telegram` → Vercel Queues → обработчик бота →
3x-ui. В PostgreSQL Supabase сохраняются контакты, подтверждения, очередь
рассылок, результаты и обработанные ID обновлений. На диск Vercel ничего не
сохраняется. Постоянный worker и cron не нужны.

### Подготовка проекта

1. Создайте или выберите отдельный проект Supabase. В **Connect** скопируйте
   PostgreSQL URI для **Session Pooler**, порт **5432**. Подставьте пароль базы
   с URL-кодированием специальных символов и `sslmode=require`. Это серверный
   `DATABASE_URL`, а не Supabase Project URL и не `anon` / publishable key.
2. Не используйте Transaction Pooler на порту 6543: обработчик использует
   session advisory lock для последовательной обработки между инстансами.
3. Импортируйте GitHub-репозиторий `ksusonic/3x-ui-telegram` в Vercel.
   Root Directory — корень репозитория, Framework — FastAPI. Python 3.12 и
   приватный обработчик очереди настроены в проекте. Регион — `fra1`.
4. В Vercel **Settings → Environment Variables**, только для **Production**,
   заполните следующие значения:

| Переменная | Содержимое |
| --- | --- |
| `BOT_TOKEN` | Токен из BotFather |
| `ADMIN_IDS` | Числовые Telegram ID админов через запятую |
| `PANEL_BASE_URL` | Доступный из Vercel HTTPS URL панели с её базовым путём |
| `PANEL_API_TOKEN` | API-токен панели; альтернатива — `PANEL_USERNAME` и `PANEL_PASSWORD` |
| `DATABASE_URL` | PostgreSQL Session Pooler URI Supabase |
| `TELEGRAM_WEBHOOK_SECRET` | Случайный секрет, 32–256 символов `A-Za-z0-9_-` |
| `SUBSCRIPTION_BASE_URL` | Необязательно: публичный префикс подписки |

Сгенерировать webhook-секрет можно локально с помощью `secrets.token_urlsafe(32)`.
Секреты храните в окружении Production, а не в `vercel.json` или Git. Для вызова
Vercel Queues на Vercel используется авторизация платформы; отдельный секрет
очереди в коде не требуется. Убедитесь, что Queues доступен в выбранном проекте.

База создаётся в отдельной схеме `vpn_bot`, которая не должна добавляться в
Supabase Exposed Schemas. Для таблиц включён RLS, публичных политик нет.
Подключение должно выполняться владельцем схемы: ему нужны права создавать
схему/таблицы и работать с ними. `anon` и `authenticated` доступ к данным не
получают. Не размещайте другие данные приложения в этой схеме.

### Развёртывание и включение

После сохранения переменных выполните production deployment. Код webhook и
подписчик очереди импортируются без секретов во время сборки; окружение читается
во время обработки запросов. Preview deployments не обрабатывают сообщения бота.

Проверьте `/health`: должен вернуть `{"ok":true}`. Это проверка загрузки приложения,
она не проверяет конфигурацию, базу или API панели. Запрос `POST /api/telegram`
без правильного `X-Telegram-Bot-Api-Secret-Token` должен получать 403, при
отсутствующей конфигурации — 503. Не отключайте защиту всего Vercel-аккаунта;
production webhook должен быть доступен Telegram без интерактивной авторизации.

Проверьте доступ к панели командой `python -m vpnbot --check-panel` с теми же
значениями панели в окружении. После проверки deployment и окружения загрузите
секреты локально в защищённое окружение и зарегистрируйте webhook:

```sh
uv run --frozen python -m vpnbot.webhook https://ВАШ-ПРОЕКТ.vercel.app/api/telegram
```

Команда задаёт secret header, разрешает только сообщения и callback-кнопки,
сохраняет ожидающие обновления и проверяет установленный адрес. Никакого
административного HTTP endpoint для установки webhook в приложении нет.
Если раньше запускался VPS polling-сервис, остановите его перед регистрацией.

После включения: `/start` от админа, привязка одного тестового клиента, выдача
подключения обычному пользователю и одна пробная рассылка. Посторонним бот
молчит. Состояние обработки проверяется в логах Vercel, разделе Queues и `/jobs`.
Входящие сообщения и credentials в логи не выводятся.

### Надёжность и ограничения

- Webhook отвечает 200 только после постановки обновления в Vercel Queues;
  повторный `update_id` использует тот же ключ идемпотентности.
- Подписчик сериализован через настройки очереди и PostgreSQL session lock.
  Это защищает и от параллельных сообщений, и от перекрытия deployment.
- Повторно доставленные обработанные обновления не запускают команды снова.
  Подтверждения привязок/рассылок одноразовые и сохраняются в базе.
- Рассылка выполняет одну отправку за вызов, затем ставит продолжение с задержкой.
  Ограничения Telegram сохраняются между вызовами. Результат `unknown` не
  отправляется заново. Продолжение публикуется до подтверждения текущей задачи.
- После аварии команда с ответом могла выполниться до отметки обработки: при
  повторе возможен повтор меню или сообщения об устаревшей кнопке. Повторное
  подтверждение не создаёт вторую рассылку и не повторяет изменение привязки.
- Telegram и Vercel Queues повторяют недоставленные задачи, но не заменяют
  мониторинг. Проверяйте ошибки, возраст ожидающих задач и ограничения плана.
- Обновления и задания очереди могут содержать Telegram-сообщения. В PostgreSQL
  VPN-ключи не сохраняются. Резервное копирование PostgreSQL настраивается
  в Supabase; SQLite backup-скрипт к этому способу запуска не относится.
- 3x-ui должна быть доступна Vercel по HTTPS. Loopback и локальные имена VPS
  из Vercel недоступны. TLS-проверка панели остаётся включённой.

Локальные интеграционные тесты PostgreSQL используют только явный
`TEST_DATABASE_URL`. **Указывайте отдельную одноразовую тестовую базу**: тесты
очищают таблицы схемы `vpn_bot`. Для обычного запуска тестов без этой переменной
PostgreSQL-сценарии пропускаются, SQLite и webhook проверяются локально.

## Возможности

| Команда | Назначение |
| --- | --- |
| `/start`, `/help` | Меню; `/start` также регистрирует личный чат для уведомлений |
| `/id` | Свой числовой Telegram ID |
| `/connections` | Свои ссылки, QR-коды и подписка, если настроена |
| `/status` | Включён ли клиент и сколько трафика использовано |
| `/instruction` | Инструкция по импорту подключения |
| `/users [поиск]` | Только админы: список клиентов, привязок и доступности для сообщений |
| `/link ID [поиск]` | Только админы: выбрать существующего клиента и подтвердить привязку |
| `/unlink ID [поиск]` | Только админы: выбрать клиента этого ID и подтвердить снятие привязки |
| `/notify ID текст` | Только админы: предварительный просмотр личного уведомления |
| `/broadcast текст` | Только админы: предварительный просмотр общей рассылки |
| `/jobs` | Только админы: последние 10 рассылок и результаты доставки |

Одному человеку можно привязать несколько клиентов. При переносе показываются
старый и новый ID. Снятие привязки закрывает доступ к боту, но не отключает VPN.
Непривязанным пользователям бот не отвечает: ни на `/start`, ни на другие команды
или кнопки. В группах бот также молчит. Если проверить привязку из-за сбоя панели
не удалось, бот не отвечает до успешной проверки доступа.

Админ должен заранее знать числовой Telegram ID пользователя. Он привязывает
его командой `/link 123456789 alice`, выбирает клиента и подтверждает изменение.
Пользователь после привязки повторяет `/start`. Запуск бота сам по себе доступа
не даёт. Бот не может первым написать человеку, который не открыл личный чат.

Уведомления отправляются обычным текстом, до 3000 символов Telegram, после
подтверждения админом. Один Telegram ID получает одно сообщение, даже если ему
назначено несколько VPN-клиентов. Новые получатели не добавляются к уже
подтверждённой рассылке. Перед каждой отправкой привязка проверяется повторно.

## Настройка

1. Создайте **отдельного** бота в BotFather через `/newbot`.
2. Отключите добавление бота в группы в BotFather (`/setjoingroups`).
   Проверка личного чата также есть в самом боте.
3. Заполните `.env.example` и сохраните как защищённый конфигурационный файл.
   Не передавайте токен в чате и не добавляйте файл с секретами в Git.
4. Задайте `ADMIN_IDS` — положительные числовые ID через запятую.
5. Задайте полный `PANEL_BASE_URL`, включая базовый путь панели.
   Пример: `https://ru-9.miem.tech:10443/ПУТЬ-ПАНЕЛИ/`.
6. Используйте `PANEL_API_TOKEN` из настроек API панели либо её логин и пароль.
   Для панели с 2FA используйте API-токен: бот не генерирует одноразовые коды.
7. При необходимости укажите `SUBSCRIPTION_BASE_URL`: публичный адрес подписки
   вместе с её настроенным префиксом. Не подставляйте сюда URL панели.

Используется HTTPS с проверкой сертификата; для своего центра сертификации
задайте `PANEL_CA_FILE`. При работе на том же сервере домен сертификата можно
направить на loopback через `/etc/hosts`. Отключения проверки TLS в боте нет.
Токен API предпочтителен для автоматизации; не предполагается, что панель
предоставляет ему отдельную ограниченную роль.

Индивидуальные ссылки берутся из API конкретного клиента. Если один `subId`
объединяет клиентов разных Telegram ID, общая подписка не выдаётся.
Ссылки и QR-коды отправляются с защитой пересылки Telegram; это не предотвращает
ручное копирование VPN-ключа.

## Локальная проверка

Нужны Python 3.12–3.14 и uv. В этом каталоге:

```sh
uv sync --frozen --python 3.12
uv run --frozen python -m pytest -q
uv run --frozen ruff check vpnbot tests
```

Приложение читает переменные окружения; само `.env` не загружает. Для локального
запуска заполните `.env`, используйте shell-кавычки вокруг значений паролей и
укажите доступный `DATABASE_PATH`, например `./state/bot.sqlite3`:

```sh
set -a
. ./.env
set +a
uv run --frozen python -m vpnbot --check-panel
uv run --frozen python -m vpnbot
```

`--check-panel` только читает список, полную запись первого клиента и его ссылки,
проверяет подготовку payload без записи, выводит лишь общее количество клиентов
и количество привязок. Токен Telegram и админы для этой команды не требуются.
Проверка не заменяет пробную привязку: права записи API так не проверяются.

## Установка на Ubuntu-сервер

Код подготовлен локально. На сервере ничего не устанавливалось, реальные
VPN-клиенты не менялись. Перед запуском проверьте API установленной версии.
Бот использует современный `/panel/api/clients`; старый API inbounds не поддерживается.

Передайте каталог `bot/` в `/opt/vpn-telegram-bot`, **без** `.venv`, `.env`, кэшей
и локальной базы. macOS-окружение `.venv` нельзя переносить на Linux.
Нужны системные пакеты `python3.12-venv`, `ca-certificates`.

Следующие команды выполняются на сервере из `/opt/vpn-telegram-bot`:

```sh
sudo useradd --system --user-group --home-dir /var/lib/vpn-telegram-bot --shell /usr/sbin/nologin vpn-telegram-bot
sudo python3.12 -m venv /opt/vpn-telegram-bot/.venv
sudo /opt/vpn-telegram-bot/.venv/bin/pip install --require-hashes -r requirements.txt
sudo install -d -m 0700 /etc/vpn-telegram-bot
sudo install -m 0600 .env.example /etc/vpn-telegram-bot/bot.env
sudoedit /etc/vpn-telegram-bot/bot.env
sudo install -m 0644 deploy/vpn-telegram-bot.service /etc/systemd/system/vpn-telegram-bot.service
sudo systemctl daemon-reload
```

Конфигурация `bot.env` читается systemd. Не вставляйте её содержимое в команды
диагностики. Для read-only проверки с тем же окружением:

```sh
sudo systemd-run --wait --pipe --collect --unit=vpn-bot-check --property=User=vpn-telegram-bot --property=WorkingDirectory=/opt/vpn-telegram-bot --property=EnvironmentFile=/etc/vpn-telegram-bot/bot.env /opt/vpn-telegram-bot/.venv/bin/python -m vpnbot --check-panel
```

Проверив результат:

```sh
sudo systemctl enable --now vpn-telegram-bot
sudo systemctl status vpn-telegram-bot --no-pager
sudo journalctl -u vpn-telegram-bot -n 50 --no-pager
```

Сервис работает от отдельного пользователя. База создаётся в
`/var/lib/vpn-telegram-bot/bot.sqlite3`; systemd создаёт этот каталог с правами 0700.
Код и `.venv` должны быть доступны сервису для чтения, но не для записи.
Файл `bot.env` остаётся доступным только root. Секреты не выводятся в лог.
Используется long polling без входящего порта. При существующем webhook бот
откажется запускаться; webhook автоматически не удаляется. Не запускайте другой
polling-сервис с тем же токеном. Lock-файл исключает два процесса с одной базой.

Первые проверки: один тестовый VPN-клиент, админ и обычный пользователь.
Проверьте выдачу и импорт подключения, снятие привязки, одну личную рассылку,
отказ постороннему и отсутствие сроков/квот. Затем привязывайте остальных.
Для остановки: `sudo systemctl stop vpn-telegram-bot`. VPN продолжает работать.

## Хранение, сбои и резервное копирование

- В 3x-ui хранится `tgId`. В SQLite — личные chat ID, временные подтверждения,
  очередь, тексты уведомлений, результаты и журнал административных действий.
  Ключи подключения и снимки записей клиентов в SQLite не сохраняются.
- Полный клиент читается перед изменением и сравнивается с подтверждённым снимком
  по хэшу. Меняется только `tgId`, остальные поля преобразуются обратно в формат
  API. После записи бот перечитывает клиента и проверяет сохранность параметров.
- API панели не предоставляет условную запись по версии. Не редактируйте того же
  клиента в панели одновременно с подтверждением в боте. При частичной ошибке
  или таймауте записи проверьте результат в 3x-ui; автоматического повтора нет.
- При недоступной панели выдача ключей закрывается, рассылки ждут восстановления.
  Блокировка бота помечает чат недоступным до нового `/start`.
- Очередь переживает перезапуск. Если процесс остановлен во время отправки или
  ответ Telegram потерян, результат `unknown` не отправляется повторно.
  Админ получает итоговый отчёт и может посмотреть `/jobs`.
- Ограничение Telegram `retry_after` откладывает всю очередь, в том числе после
  перезапуска. Обычная очередь отправляет примерно одно сообщение в секунду.
- Завершённые рассылки старше 30 дней очищаются при запуске. Журнал админских
  действий сохраняется. Конфигурацию с токенами храните отдельно от бэкапа базы.

Существующий бэкап 3x-ui не включает SQLite бота. Для согласованного снимка
используйте `deploy/backup.py`, а не копирование только основного файла при
работающем WAL. Например, из ежедневного задания резервного копирования:

```sh
sudo python3 /opt/vpn-telegram-bot/deploy/backup.py /var/lib/vpn-telegram-bot/bot.sqlite3 /ЗАЩИЩЁННЫЙ-КАТАЛОГ/bot.sqlite3
```

Снимок содержит тексты уведомлений и Telegram ID; храните его в шифрованном
хранилище. Интеграцию с серверным restic нужно выполнить при развёртывании.
Для восстановления остановите бота, верните SQLite без старых WAL/SHM-файлов,
назначьте владельца `vpn-telegram-bot`, затем запустите сервис. Незавершённые
отправки с неопределённым результатом после восстановления также не повторяются
автоматически; ещё не начатые отправки остаются в очереди.

## Источники API

Реализация сверена с официальными [OpenAPI](https://github.com/MHSanaei/3x-ui/blob/main/docs/public/openapi.json),
[обработчиком клиентов](https://github.com/MHSanaei/3x-ui/blob/main/internal/web/controller/client.go)
и [моделью](https://github.com/MHSanaei/3x-ui/blob/main/internal/database/model/model.go).
API, которые использует бот: `GET clients/list`, `GET clients/get/{email}`,
`GET clients/links/{email}`, `POST clients/update/{email}` под `/panel/api/`;
при авторизации паролем — `POST login` относительно базового пути панели.
Прочие операции записи панели бот не вызывает.
